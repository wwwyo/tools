# ケイリョウ（keiryo）

画像の圧縮率を工程ごとに比較します。

## 使い方

- 画像をドラッグ&ドロップ / クリックで選択 / Cmd+V で貼り付け、または「サンプル画像で試す」
- 読み込むと、ドットグリッドのキャンバス上に「元画像 → サイズ → フォーマット → メタデータ → 出力」の5ノードが並ぶ。ノードは選んでいる値を反映するだけの読み取り専用の表示で、コントロールを一切持たない。左右の縁にポート（入出力の端子）を持ち、ポート同士を曲線のエッジで繋ぐ。ノードをクリック（または ← / → キー）すると、そのノードのインスペクタカードがキャンバス下に開く。常にちょうど1ノードがアクティブで、読み込み直後は「元画像」が開いている
- パラメータはインスペクタカード側に持つ。各カードは操作対象のノードに応じたコントロール行（select・range・checkbox・ダウンロードボタン）を先頭に持ち、その下に既存の詳細内容（テーブル・比較表・before/after 画像）が続く。コントロール要素はノード選択やパイプライン再計算のたびに作り直さず、値の変更中にフォーカスを失わない
- エッジの太さは、そのエッジを流れた後のバイト数を元ファイルに対する比率で表す（最小 1.5px・最大 8px）。段を追うごとに配線が細くなっていく様子がそのまま軽量化の進み具合になる。エッジ中央のラベルには通過後のバイト数と、直前のエッジとの差分（変化がある場合のみ）を表示する。再計算中はエッジが流れるような破線アニメーションになる（reduced motion では無効）
- 「元画像」カード: コントロールなし。サムネイルと検品テーブル（ファイル名・拡張子・実際の形式・MIME・容量・寸法・画素数・アスペクト比・最終更新・透過の有無・色深度・EXIF 向き）が出る。拡張子と実形式が食い違っていれば警告行が出る
- 「サイズ」カード: コントロール行に長辺の上限（なし / 2048 / 1600 / 1200 / 800px。画像の長辺以上の値は選べない）と品質（0.3〜1.0 のスライダー）を持つ。長辺の上限が「なし」なら素通し、それ以外は元と同じ形式のまま canvas で縮小・再エンコードする。ノードは縮小前後の寸法（例: `1600×1067 → 1200×800`）の要約行だけを表示する。カード本体には寸法・縮小率・画素数・容量の情報テーブルに加え、原寸/2048/1600/1200/800 の5段を同じ品質・同じ元フォーマットで揃えた what-if の棒グラフ比較（長辺ごとの比較）が出る。選択中の長辺の段を強調表示する
- 「フォーマット」カード: コントロール行に出力形式（元のまま / JPEG / WebP / PNG / AVIF。書き出せない形式はブラウザ probe の結果に基づき disabled）と品質スライダーを持つ。品質はサイズカードの品質と同じ状態を指し、どちらを動かしても両方に反映される。ノードは `JPEG → WebP` のような変換前後の形式ラベルと現在の品質値の要約行だけを表示する。カード本体には対応している全形式（JPEG/WebP/PNG/AVIF）の圧縮率比較を棒グラフの行（寸法・容量・差分%・比例バー）で表示し、現在選んでいる形式の行を強調する
- 「メタデータ」カード: コントロール行に「メタデータを除去」のチェックボックスを持つ。ノードは検出バイト数と除去したかどうかの要約行（再エンコード済みなら「再エンコードで除去済み」）だけを表示する。カード本体には元ファイルの Exif / XMP / ICC / コメント等のセグメント一覧とバイト数を表示する
- 「出力」カード: コントロール行にダウンロードボタンを持つ（計算中は disabled）。ノードは最終的な容量・差分の要約行だけを表示する。カード本体には寸法・形式・容量の情報テーブルと、元画像との before/after 比較画像が出る
- 解析・変換はすべてページ内 Canvas で完結し、画像は外部に送信しない

## 設計と判断

### 拡張子の一覧ではなく工程のパイプラインにした理由

このツールで効くレバーは拡張子だけではなく、縮小・再エンコード・メタデータ除去がそれぞれ独立に効く。これらを「行 = 拡張子」の一覧に押し込めると「今どの設定がどれだけ効いているか」が行の増殖でしか表現できなくなる。工程を「元画像 → サイズ → フォーマット → メタデータ → 出力」の直列パイプラインとして並べ、各ノードが自分の入力から出力までの差分だけを背負う形にすると、レバーとその効果が1対1で対応する。

### ノードの並び順

寸法変更（サイズ）は非可逆圧縮より先に決まっていないと「同じ設定で比較している」と言えない。フォーマット選択はメタデータの有無に影響する（後述）ため、メタデータより前に置く。メタデータ除去は最終出力の直前の仕上げなので出力の手前に置く。この順は「値が確定してから次を評価する」依存関係そのものであり、途中の順序を入れ替える余地がない。

### サイズ段が元と同じ形式で再エンコードする理由

サイズ段の問いは「拡張子は変えずに縮小するとどれだけ軽くなるか」であって、フォーマット変更の効果と混ぜたくない。フォーマット変更の効果は次のフォーマット段に切り出してあるので、サイズ段では変数を1つ（寸法）だけ動かす。GIF / AVIF / HEIC など canvas から直接再エンコードできない形式は JPEG にフォールバックする（そのままでは書き出せないため）。

### フォーマット比較表がフォーマット段の詳細にある理由

比較表は「今の寸法・品質のまま、拡張子だけ変えたらどうなるか」を見せるものなので、フォーマット段の入力（サイズ段の出力）に対する差分として意味を持つ。フォーマットノードの詳細パネルに置くことで、選んでいる形式と比較表の基準が同じ土俵にあることが一目でわかる。表は逐次計算する（Promise.all にしない）。大きな画像で複数枚分のフルサイズ canvas を同時に確保するとメモリを食い荒らすため。サイズノードの詳細パネルにも同じ形式で、原寸/2048/1600/1200/800 を同じ品質のまま並べる what-if 比較（長辺ラダー）を持つ。パイプライン本体（ノード・エッジ）は「今選んでいる経路」だけを表し、「他を選んだらどうなるか」の比較はすべて詳細パネル側に寄せている。

### メタデータ除去をロスレスにし、canvas 経由後は「除去済み」と報告する理由

サイズ段またはフォーマット段で canvas 再エンコードが起きていれば、その時点で Exif 等のメタデータは既に失われている。ここで改めて「除去した」と主張すると、何もしていないのに手柄を主張することになるため、メタデータ段は「再エンコード時に除去済み（元 N KB）」と事実をそのまま報告する。逆に、サイズ・フォーマットともに素通しで元ファイルのバイト列がまだ生きている場合は、メタデータ段が実際にロスレスな除去を行う。JPEG は APPn マーカー（Exif / XMP / ICC / Photoshop / COM）を、PNG は補助チャンク（tEXt / zTXt / iTXt / eXIf / iCCP / tIME）を、デコードに必要な部分は一切変更せず読み飛ばして再構築する。

### WebP のメタデータ除去は未対応と明示する理由

WebP は EXIF / XMP / ICCP チャンクを読み飛ばすだけでは済まない。RIFF 全体のサイズと拡張ヘッダー VP8X の flags ビット（各チャンクの有無を示す）を整合させて書き換える必要があり、ここを誤ると壊れたファイルを生成してしまう。安全側に倒し、検出（セグメント一覧・合計バイト数の表示）だけ行い除去は行わない。トグルを on にしても「WebP の除去は未対応です」とそのまま伝え、無言でスキップしない。

### 未対応の出力形式を隠さず disabled で残す理由

非対応ブラウザで無言で別形式に差し替えると、聞きたかった形式の答えが返ってこないことに気づきにくい。選択肢として残したまま disabled にし「このブラウザでは書き出し不可」と明示することで、比較材料が足りていないという事実がそのまま伝わる。対応可否は起動時に 1×1 canvas への `toBlob` で実機 probe し、返ってきた `blob.type` が要求した mime と一致するかで判定する（無言で別形式を返すブラウザがあるため）。

### 品質をパイプライン全体で1つの共通設定にした理由

品質基準がノードごとに違うと「サイズ段だけ縮小した」「フォーマット段だけ変換した」の比較が別の物差しになってしまう。品質は変数を1つに保つための全体共通のグローバル設定とし、`state.quality` 1箇所に持たせる。サイズ・フォーマット両カードの品質スライダーはこの1つの値を映す2枚のビューで、どちらを動かしても両方・パイプライン全体に同じ値が反映される。

### 各ノードを都度 canvas 再計算する構成にした理由（前段の出力を使い回さない）

ノードをまたいで同じ canvas / blob を使い回すと、あるノードの結果を理解するのに前段の内部状態を知る必要が出てくる。各ノードは「元画像 + 長辺上限 + 品質 + 出力形式」から都度必要な出力を計算し直す設計にし、ノード単体で完結させた。PoC 規模の画像サイズでは、この再計算コストは体感できる差にならない。

### 逐次エンコード（Promise.all にしない）

サイズ段・フォーマット比較表ともに、複数回の `canvas.toBlob` を並列実行すると大きな画像では同時に複数枚分のフルサイズ canvas を確保することになりメモリを食う。1件ずつ await して順番に確定させ、パイプライン全体の再計算も debounce（150ms）+ 実行中の変更は直後にもう一度だけやり直す直列化で対応する。

### ノードの入場アニメーションは画像読み込み時の1回だけ

ノード要素は画像読み込みごとに1回だけ生成し、以降のパラメータ変更による再計算では中身の更新だけを行って要素は作り直さない。パラメータを動かすたびに入場アニメーションが再生されると、値の変化そのものより演出が気になってしまうため。

### AVIF だけ wasm エンコーダを積んでいる理由

ブラウザは AVIF を「表示」はできても、`canvas.toBlob("image/avif")` で「書き出す」実装はどこにもない。AVIF を実データとして比較材料に出すには自前のエンコーダが要るため、`@jsquash/avif`（libavif を wasm 化したもの。Apache-2.0）をバンドルし、canvas から取り出した `ImageData` を直接エンコードしている。対応可否は他の形式のような `toBlob` probe ではなく `typeof WebAssembly === "object"` の一点で判定する。この wasm は `import("@jsquash/avif")` で AVIF を実際に使う瞬間まで読み込みを遅らせ、一度読み込んだモジュールは Promise ごとキャッシュして使い回す（AVIF を選ばないユーザーに wasm を配らないため）。1600px 級の画像で数秒かかるほど遅いため、比較表・COMPARISON_FORMATS の両方で常に最後に置き、フォーマット比較表では他の行を待たせず pending 行のまま先に確定させて後から差し替える（フォーマットノードにも「AVIF を変換中…」を出す）。選択中の出力形式が AVIF のときだけ、この同じ encode 結果を選択出力にも使い回し、二重にエンコードしない。

### ヘッダー読み取りは 64 KiB

フォーマット判定と PNG IHDR は先頭 32 byte で足りるが、JPEG の Exif（APP1）セグメントは 16bit 長で最大 64 KiB になりうる。Orientation タグ・メタデータセグメント走査の両方が届くよう、ヘッダーはまとめて 64 KiB 読む。画像全体を ArrayBuffer に載せないのは、巨大ファイルでメモリを二重に持たないため。

## ファイル構成

```
keiryo/
├── index.html       エントリ（title / description は一覧・OGP 自動生成に使われる）
├── main.ts           UI・状態管理・DOM 組み立て・パイプライン実行のオーケストレーション
├── pipeline.ts        各ノードの計算ロジックと、詳細パネル用マークアップの組み立て
├── imageMeta.ts       マジックナンバー判定・PNG IHDR・JPEG Exif Orientation・透過検知・検品メタデータ組み立て
├── metadataStrip.ts    メタデータセグメント/チャンクの検出とロスレス除去（JPEG / PNG）、WebP は検出のみ
├── encode.ts          長辺キャップ付きリサイズ・canvas 再エンコード・書き出し対応 probe・サンプル画像生成
├── styles.css         :root テーマ上書き・ノードの入場アニメーション・比率バーの transition
└── og.tsx             OGP カード用の画面ミニチュア（パイプラインのノード＋矢印＋比率バーを再現）
```
