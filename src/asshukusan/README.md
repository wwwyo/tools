# 圧縮 san（asshukusan）

画像の圧縮率を工程ごとに比較します。

## 使い方

- 画像をドラッグ&ドロップ / クリックで選択 / Cmd+V で貼り付け、または「サンプル画像で試す」
- 読み込むと、ドットグリッドのキャンバス上に「元画像 → サイズ → フォーマット → メタデータ → 出力」の5ノードが並ぶ。ノードは選んでいる値を反映するだけの読み取り専用の表示で、コントロールを一切持たない。左右の縁にポート（入出力の端子）を持ち、ポート同士を曲線のエッジで繋ぐ。ノードをクリック（または ← / → キー）すると、そのノードのインスペクタカードがキャンバス下に開く。常にちょうど1ノードがアクティブで、読み込み直後は「元画像」が開いている
- パラメータはインスペクタカード側に持つ。操作を持つカード（フォーマットの品質スライダー、メタデータのセグメント除去チェックボックス・Exif 編集欄）は先頭にコントロール行を持ち、その下に詳細内容（テーブル・比較表・before/after 画像）が続く。サイズ・出力の2カードはコントロール行を持たず、what-if 行やダウンロードボタンが詳細内容の中で選択肢・操作を兼ねる。コントロール要素はノード選択やパイプライン再計算のたびに作り直さず、値の変更中にフォーカスを失わない
- エッジの太さは、そのエッジを流れた後のバイト数を元ファイルに対する比率で表す（最小 1.5px・最大 8px）。段を追うごとに配線が細くなっていく様子がそのまま軽量化の進み具合になる。エッジ中央のラベルには通過後のバイト数と、直前のエッジとの差分（変化がある場合のみ）を表示する。再計算中はエッジが流れるような破線アニメーションになる（reduced motion では無効）
- 「元画像」カード: コントロールなし。サムネイルと検品テーブル（ファイル名・拡張子・実際の形式・MIME・容量・寸法・画素数・アスペクト比・最終更新・透過の有無・色深度・EXIF 向き）が出る。拡張子と実形式が食い違っていれば警告行が出る
- 「サイズ」カード: コントロール行を持たない（品質はフォーマットカードで動かす唯一の入力で、このカードは品質を一切操作しない）。長辺の上限を選ぶ操作は select を持たず、カード本体の what-if 比較（長辺ごとの比較。原寸/2048/1600/1200/800 の5段）の行そのものが選択肢を兼ねる。各行は行全体をヒットエリアに持つ radio ボタンで、クリック（または Tab で移動して Enter/Space、フォーカス中の ↑/↓）で選ぶ。長辺の上限が「原寸」なら素通し、それ以外は元と同じ形式のまま canvas で縮小・再エンコードする。画像の長辺以上（拡大になる）段は disabled で残し、寸法・容量の代わりに「拡大になるため不可」と表示する。選択中の行は枠線とハイライトで強調し、ノードは縮小前後の寸法（例: `1600×1067 → 1200×800`）の要約行だけを表示する。カード本体には寸法・縮小率・画素数・容量の情報テーブルも出る
- 「フォーマット」カード: コントロール行には品質スライダーだけを持つ（サイズカードは品質を持たないため、これがアプリ全体で唯一の品質入力）。出力形式を選ぶ操作は select を持たず、カード本体の「形式ごとの比較」表（元のまま/JPEG/WebP/PNG/AVIF）の行そのものが選択肢を兼ねる。「元のまま」行はサイズ段の出力をそのまま基準として先頭に並び、各行は寸法・容量・差分%・比例バーを持つ radio ボタン（サイズカードと同じ行 UI）。書き出せない形式はブラウザ probe の結果に基づき disabled で残し「このブラウザでは書き出し不可」と表示する。選択中の行を強調し、ノードは `JPEG → WebP` のような変換前後の形式ラベルと現在の品質値の要約行だけを表示する
- 「メタデータ」カード: コントロール行にセグメント（Exif / XMP / ICC / APP13 / COM / PNG テキストチャンク）ごとの「除去」チェックボックスを持つ（ICC_PROFILE だけ既定で保持）。各セグメント行はチェックボックス+名前+バイト数の1行目に続けて、平易な日本語の説明（例: 「撮影情報（機種・日時・向き・GPS など）」）を2行目に、安価に読める中身のプレビュー（PNG tEXt/iTXt の `keyword: text`、zTXt/iCCP は展開せず keyword だけ、JPEG COM のコメント文字列、APP1 XMP のサイズと拾えれば CreatorTool/creator、ICC プロファイルの `desc` タグから読んだプロファイル名）があれば3行目に表示する。JPEG の APP1 Exif・PNG の eXIf のどちらかがあるときは、行の下にその IFD0 / Exif IFD 全エントリのタグテーブル（インデント表示）が展開される。各タグ行は「消す」チェックボックス+タグ名（未知のタグは `0x829A` の16進表記）+値+サイズを持ち、Orientation / DateTime / DateTimeOriginal の3タグだけは値欄が編集フォーム（Orientation の select、DateTime 系のテキスト入力）になっていて、そのタグの「消す」を ON にすると編集欄が disabled になる。ポインタタグ（ExifIFDPointer/GPSInfoPointer）と範囲外・構造に重なる「（壊れた値）」判定のタグはセグメント構造そのものなのでチェックボックスを持たない。GPS はテーブル最後の疑似行（`GPS IFD`）として、既存の「GPS 情報を消す」チェックボックスと緯度経度表示をそのまま持つ。セグメントの「除去」チェックボックスを ON にすると、タグテーブル全体が dim して個別操作を無効化する（セグメント除去が優先されるため）。ノードは「除去 N B / 保持 M B」（タグを個別に消していれば「Exif タグ N 件を消去」も追加）、または canvas 出力時の引き継ぎ状況を要約行として表示する。カード本体には除去/保持の合計と、状態説明のノート（タグ消去はファイルサイズを変えないことの注記を含む）が並ぶ
- 「出力」カード: カード上部にもダウンロードボタンを持つ（出力ノードのボタンと同じ href・ファイル名を指し、計算中は両方 disabled になる）。ノードは最終的な容量・差分の要約行だけを表示する。カード本体には寸法・形式・容量の情報テーブルと、元画像との before/after 比較画像が出る
- 解析・変換はすべてページ内 Canvas で完結し、画像は外部に送信しない

## 設計と判断

### 拡張子の一覧ではなく工程のパイプラインにした理由

このツールで効くレバーは拡張子だけではなく、縮小・再エンコード・メタデータ除去がそれぞれ独立に効く。これらを「行 = 拡張子」の一覧に押し込めると「今どの設定がどれだけ効いているか」が行の増殖でしか表現できなくなる。工程を「元画像 → サイズ → フォーマット → メタデータ → 出力」の直列パイプラインとして並べ、各ノードが自分の入力から出力までの差分だけを背負う形にすると、レバーとその効果が1対1で対応する。

### ノードの並び順

寸法変更（サイズ）は非可逆圧縮より先に決まっていないと「同じ設定で比較している」と言えない。フォーマット選択はメタデータの有無に影響する（後述）ため、メタデータより前に置く。メタデータ除去は最終出力の直前の仕上げなので出力の手前に置く。この順は「値が確定してから次を評価する」依存関係そのものであり、途中の順序を入れ替える余地がない。

### サイズ段が元と同じ形式で再エンコードする理由

サイズ段の問いは「拡張子は変えずに縮小するとどれだけ軽くなるか」であって、フォーマット変更の効果と混ぜたくない。フォーマット変更の効果は次のフォーマット段に切り出してあるので、サイズ段では変数を1つ（寸法）だけ動かす。GIF / AVIF / HEIC など canvas から直接再エンコードできない形式は JPEG にフォールバックする（そのままでは書き出せないため）。

### フォーマット比較表がフォーマット段の詳細にある理由

比較表は「今の寸法・品質のまま、拡張子だけ変えたらどうなるか」を見せるものなので、フォーマット段の入力（サイズ段の出力）に対する差分として意味を持つ。フォーマットノードの詳細パネルに置くことで、選んでいる形式と比較表の基準が同じ土俵にあることが一目でわかる。表は逐次計算する（Promise.all にしない）。大きな画像で複数枚分のフルサイズ canvas を同時に確保するとメモリを食い荒らすため。サイズノードの詳細パネルにも同じ形式で、原寸/2048/1600/1200/800 を同じ品質のまま並べる what-if 比較（長辺ラダー）を持つ。パイプライン本体（ノード・エッジ）は「今選んでいる経路」だけを表し、「他を選んだらどうなるか」の比較はすべて詳細パネル側に寄せている。

### メタデータ除去をロスレスにし、canvas 経由後は「除去済み」と報告する理由

サイズ段またはフォーマット段で canvas 再エンコードが起きていれば、その時点で Exif 等のメタデータは既に失われている。ここで改めて「除去した」と主張すると、何もしていないのに手柄を主張することになるため、メタデータ段は事実をそのまま報告する。逆に、サイズ・フォーマットともに素通しで元ファイルのバイト列がまだ生きている場合は、メタデータ段が実際にロスレスな除去を行う。JPEG は APPn マーカー（Exif / XMP / ICC / Photoshop / COM）を、PNG は補助チャンク（tEXt / zTXt / iTXt / eXIf / iCCP / tIME）を、デコードに必要な部分は一切変更せず読み飛ばして再構築する。

### 除去をチェックボックス1個ではなくセグメント単位にした理由

「メタデータを除去」という単一トグルは、Exif は消したいが ICC は残したい（色が変わるため）というような、実際によくある要求に応えられない。`MetadataSegment` に安定な `id`（`${name}#${index}`）とバイト範囲（`start`/`end`）を持たせ、`stripMetadata` に「除去する id の集合」を渡す形に変えた。既定値は Exif / XMP / APP13 / COM / PNG テキストチャンクを除去 ON、ICC_PROFILE だけ除去 OFF にしている。ICC は色空間の定義そのものであり、sRGB でない prof を無言で捨てると色味が変わりうるため、既定で守る側に倒し、その理由をチェックボックスの隣に注記する。

### セグメント名だけでなく説明・中身プレビューを添えた理由

`APP1 XMP` や `iCCP` のようなセグメント名は、規格を知らないと何を消すことになるのか分からない。チェックボックスの隣に平易な日本語の一言（`segmentDescription`, `metadataStrip.ts`）を必ず出し、加えて「解凍・重い解釈をせずに安価に読める」中身だけをプレビューする（`segmentContentPreview`）。PNG の `tEXt`/`iTXt` はテキストをそのまま `keyword: text` で見せるが、`zTXt` と `iCCP` の本体は zlib 圧縮のため展開せず、`zTXt` はキーワードだけ、`iCCP` は圧縮前に無圧縮で並んでいるプロファイル名（keyword）だけを見せる。JPEG の APP1 XMP は XML をそのまま出さず、サイズと拾えれば `CreatorTool`/`dc:creator` の値だけを添える。ICC（JPEG の APP2 ICC_PROFILE）はヘッダー直後のタグテーブル（オフセット 128）から `desc` タグを探し、`textDescriptionType`（ASCII）と `mluc`（UTF-16BE）の両方に対応してプロファイル名を表示する。APP1 Exif / PNG eXIf はここでは中身を出さない。詳細は次項の「Exif 詳細」テーブルが別途担う。

### PNG の eXIf も Exif テーブル・編集の対象にした理由

PNG の `eXIf` チャンクは中身が生の TIFF（Exif の IFD 構造そのもの）で、JPEG の APP1 Exif payload から `"Exif\0\0"` の6byteヘッダーを外しただけの形をしている。この違いだけを吸収すれば `exif.ts` の `parseExifStructure`/`readExifTags`/`applyExifEdits` は形式を意識せず共有できるため、`extractExifPayload`（`exif.ts`）が JPEG は `extractExifPayloadFromJpegHeader` を、PNG は `eXIf` チャンクの中身に疑似ヘッダー（`EXIF_PAYLOAD_HEADER`）を被せたものを、どちらも同じ payload 形式で返す。編集を書き戻すときは疑似ヘッダーを剥がして生 TIFF に戻し、PNG チャンクのデータ部を上書きする（`patchPngChunkData`, `metadataStrip.ts`）。PNG チャンクは type+data に対する CRC-32 を持つため、上書き後に `crc32`（zlib と同じ多項式のテーブル実装、`metadataStrip.ts` に追加）で再計算しないと壊れたファイルになる。canvas 再エンコード後の再挿入（下記）は従来どおり JPEG 限定のままで、PNG はロスレス経路（canvas を経ない）でのみ編集・除去ができる。

### Exif の編集を「既存の固定長フィールドの in-place 上書き」に限定した理由

Exif は IFD（tag/type/count/value-or-offset の 12 byte エントリの列）の入れ子構造で、エントリの追加・削除や ASCII の count 変更は後続の全オフセットをずらす。ここまでやると「セグメント境界だけ動かして中身は解釈しない」というこのツール全体の設計（除去がロスレスである根拠）を壊してしまう。そこで `exif.ts` の `applyExifEdits` は、既存のエントリの value/offset フィールドをその場で書き換えるだけに限定した: Orientation は SHORT 1個をそのまま差し替え、DateTime 系は count と同じ 19 文字 + NUL のときだけ許可し、合わなければ書き込まずに弾く。それ以上の自由な編集（タグの追加や説明文の書き換えなど）は対象外とし、UI にも編集可能なフィールドしか出さない。

### canvas 出力への再挿入を JPEG 限定にし、Orientation を 1 に強制し、ICC を落とす理由

サイズ・フォーマット段で canvas を経由すると Exif 等は完全に失われるが、出力形式が JPEG であれば、元ファイルの APP1 Exif / APP1 XMP / COM を（除去チェックを外したものだけ）そのまま新しい JPEG の SOI 直後（APP0 があればその後）に挿し込める。WebP / PNG / AVIF は Exif の入れ物自体が別物（RIFF チャンク・非対応・ISOBMFF 系）のため引き継げず、その旨をそのまま表示してセグメントの選択操作を disabled にする。ICC は canvas が常に sRGB のピクセルを吐く以上、元の（sRGB でないかもしれない）プロファイルを持ち込むと実際の色と食い違うため、canvas 出力へは常に持ち込まない。Orientation は `drawImage` の時点で既に画素として回転済みなので、Exif の Orientation をそのまま引き継ぐと二重に回転がかかる。再挿入する Exif は常に Orientation=1 に上書きする。

### GPS 除去をゼロ埋め + IFD 参照断ちにした理由

ファイルサイズを変えない制約（セグメント境界だけを動かす設計）の下では、GPS の生バイトを物理的にファイルから消すことはできない。そこで `zeroOutGps`（`exif.ts`）は、GPS IFD の各エントリの値領域（4 byte を超えるものはオフセット先、それ以外はエントリ内の value フィールド自体）をゼロで上書きしたうえで、GPS IFD のエントリ数を 0 に、IFD0 の GPSInfo ポインタのタグ id を `0xFFFF`（private/unused）に書き換える。座標値そのものが残っていない上に標準的な Exif リーダーは IFD からたどり着けないため、実質的に GPS 情報は失われる。

### タグ単位の除去も「ゼロ埋め + タグ id 0xFFFF」にし、IFD を作り直さない理由

GPS 除去と同じ制約（エントリの追加・削除は後続オフセットをずらすため扱わない、本ファイル冒頭コメント）が個々のタグの除去にもそのまま当てはまる。`removeExifTag`（`exif.ts`）は、消したいタグの値領域（4 byte を超える分は外部オフセット先、それ以外はエントリ内の value フィールド自体）をゼロで上書きし、タグ id を `0xFFFF`（private/unused）に書き換えるだけで、IFD のエントリ数や他エントリの並びには一切触れない。GPS IFD ごと消す処理と実装を共通化できるほど考え方が同じであり、かつ IFD 全体を作り直す複雑さを避けられる。MakerNote（0x927C）のような大きな不透明データも、この「4 byte を超える値は外部領域をゼロ埋めする」という共通ロジックがそのまま効くため、タグ別の特別扱いは不要だった。

### タグ除去がファイルサイズを変えない理由

上記の通りゼロ埋めは値の中身を消すだけで、値が占めていたバイト数そのものは変わらない。セグメント境界を動かさない設計の直接の帰結として、Exif タグを何個消してもファイル全体のバイト数は変化しない。サイズを実際に減らしたい場合は、タグ単位の消去ではなく Exif セグメントごと除去する必要があり、この違いをメタデータカードの注記でそのまま伝えている。

### ポインタタグ（ExifIFDPointer / GPSInfoPointer）を消せない理由

`listExifEntries` は IFD0 の一部として ExifIFDPointer・GPSInfoPointer もタグテーブルに出すが、これらは値ではなく Exif IFD / GPS IFD 自体の位置を指すセグメント構造そのものである。ここを `0xFFFF` に書き換えて壊すと、そのポインタが指す IFD ごと読めなくなり（Exif IFD 配下の DateTimeOriginal 等も巻き添えで消える）、「このタグ1個だけを消す」という利用者の意図を裏切る。そのため `isExifEntryRemovable` はこの2タグを常に除去不可として扱い、UI 側もチェックボックスを出さない（GPS IFD をまとめて消したい場合は、専用の `GPS IFD` 疑似行の「GPS 情報を消す」チェックボックスを使う）。

### WebP のメタデータ除去は未対応と明示する理由

WebP は EXIF / XMP / ICCP チャンクを読み飛ばすだけでは済まない。RIFF 全体のサイズと拡張ヘッダー VP8X の flags ビット（各チャンクの有無を示す）を整合させて書き換える必要があり、ここを誤ると壊れたファイルを生成してしまう。安全側に倒し、検出（セグメント一覧・合計バイト数の表示）だけ行い除去は行わない。トグルを on にしても「WebP の除去は未対応です」とそのまま伝え、無言でスキップしない。

### 未対応の出力形式を隠さず disabled で残す理由

非対応ブラウザで無言で別形式に差し替えると、聞きたかった形式の答えが返ってこないことに気づきにくい。選択肢として残したまま disabled にし「このブラウザでは書き出し不可」と明示することで、比較材料が足りていないという事実がそのまま伝わる。対応可否は起動時に 1×1 canvas への `toBlob` で実機 probe し、返ってきた `blob.type` が要求した mime と一致するかで判定する（無言で別形式を返すブラウザがあるため）。

### 品質の操作をフォーマットカード1箇所に絞った理由

品質基準がノードごとに違うと「サイズ段だけ縮小した」「フォーマット段だけ変換した」の比較が別の物差しになってしまう。品質は変数を1つに保つための全体共通の設定とし、`state.quality` 1箇所に持たせる。入力もフォーマットカードの range 1つだけにし、サイズカードには置かない。同じ値を2か所から書き込める形にすると、どちらが発生源かが曖昧になり同期コードだけが増える。

### 各ノードを都度 canvas 再計算する構成にした理由（前段の出力を使い回さない）

ノードをまたいで同じ canvas / blob を使い回すと、あるノードの結果を理解するのに前段の内部状態を知る必要が出てくる。各ノードは「元画像 + 長辺上限 + 品質 + 出力形式」から都度必要な出力を計算し直す設計にし、ノード単体で完結させた。PoC 規模の画像サイズでは、この再計算コストは体感できる差にならない。

### 逐次エンコード（Promise.all にしない）

サイズ段・フォーマット比較表ともに、複数回の `canvas.toBlob` を並列実行すると大きな画像では同時に複数枚分のフルサイズ canvas を確保することになりメモリを食う。1件ずつ await して順番に確定させ、パイプライン全体の再計算も debounce（150ms）+ 実行中の変更は直後にもう一度だけやり直す直列化で対応する。

### ノードの入場アニメーションは画像読み込み時の1回だけ

ノード要素は画像読み込みごとに1回だけ生成し、以降のパラメータ変更による再計算では中身の更新だけを行って要素は作り直さない。パラメータを動かすたびに入場アニメーションが再生されると、値の変化そのものより演出が気になってしまうため。

### AVIF だけ wasm エンコーダを積んでいる理由

ブラウザは AVIF を「表示」はできても、`canvas.toBlob("image/avif")` で「書き出す」実装はどこにもない。AVIF を実データとして比較材料に出すには自前のエンコーダが要るため、`@jsquash/avif`（libavif を wasm 化したもの。Apache-2.0）をバンドルし、canvas から取り出した `ImageData` を直接エンコードしている。対応可否は他の形式のような `toBlob` probe ではなく `typeof WebAssembly === "object"` の一点で判定する。この wasm は `import("@jsquash/avif")` で AVIF を実際に使う瞬間まで読み込みを遅らせ、一度読み込んだモジュールは Promise ごとキャッシュして使い回す（AVIF を選ばないユーザーに wasm を配らないため）。1600px 級の画像で数秒かかるほど遅いため、比較表・COMPARISON_FORMATS の両方で常に最後に置き、フォーマット比較表では他の行を待たせず pending 行のまま先に確定させて後から差し替える（フォーマットノードにも「AVIF を変換中…」を出す）。選択中の出力形式が AVIF のときだけ、この同じ encode 結果を選択出力にも使い回し、二重にエンコードしない。

### pixel 処理（リサイズ + 再エンコード）を worker に逃がす理由

`encodeImage`（canvas への drawImage・toBlob、AVIF の wasm エンコード）はどれも大きな画像では数百ms〜数秒かかり、メインスレッドで実行するとその間ページ全体が固まる。`encode.worker.ts` に module worker を1体だけ遅延生成し、`OffscreenCanvas` 上で描画・エンコードまで完結させることで、UI（ノードのクリック・スライダー操作）を触れる状態に保ったまま処理する。worker 内の実処理は 1 件ずつだが、呼び出し要求は重なりうる。AVIF はキューで最新へ合流する（品質スライダーのドラッグ中などに積み上がった AVIF リクエストは `pipeline.ts` の `scheduleAvifEncode` が「実行中は1本、その間に来た分は最新の1件だけ」に間引いてから worker へ渡す。他形式は各段が直列に await する設計のため実質的に1件ずつしか飛ばない）。リクエストごとに worker を作り直す・複数体持つ利点がなく、生成コストと（AVIF を選んだ場合の）wasm の二重ロードを避けられる。メインスレッドは `createImageBitmap(img)` でビットマップを作り、Transferable として worker へ move するだけに留め、画素データのコピーは発生させない。`OffscreenCanvas`/`Worker`/`createImageBitmap` が使えない環境（古い Safari 等）だけ `encodeImageMainThread`（`encode.ts`）にフォールバックし、メインスレッドで完結させる。メタデータ段（バイト列の読み飛ばし・再挿入）は画像全体のデコード・エンコードを伴わない軽い処理のため、worker へは移さずメインスレッドに残した。書き出し対応 probe（`detectFormatSupport`）も 1×1 canvas の軽い処理のままメインスレッドに残している。

### 検品時のヘッダー読み取りをまとめて 64 KiB にしている理由

フォーマット判定と PNG IHDR は先頭 32 byte で足りるが、JPEG の Exif（APP1）セグメントは 16bit 長で最大 64 KiB になりうる。Orientation タグ・メタデータセグメント走査の両方が届くよう、画像読み込み直後の検品（`imageMeta.ts` の `extractMetadata`）ではヘッダーをまとめて 64 KiB だけ読む。これは「本編集で使う全体を読む前に、軽い検品だけ先に済ませる」ための最適化であり、画像全体を ArrayBuffer に載せないという意味ではない。実際、パイプライン本体（`main.ts` の `handleFileSelected`）はこの直後に `file.arrayBuffer()` でファイル全体を読み、`state.originalArrayBuffer` として保持し続ける。メタデータの走査・除去・Exif 編集（`metadataStrip.ts` / `exif.ts`）はどれもこの全体バッファを前提に動く。
